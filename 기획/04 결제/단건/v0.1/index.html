라이언이 추천한 특정 식당의 특정 메뉴를 사용자가 결제하는 도메인. 구독 결제(v0.2)와 별 도메인으로 분리. 단건 = 일회성, 메뉴·식당·시간 컨텍스트가 핵심, 환불 정책이 시간 기반. 결제수단·PG SDK·UX 패턴은 구독 도메인과 공유해 사용자 학습 비용 ↓.

그레이스케일 (와이어프레임) 라인 아이콘 강조는 굵기·보더·outline로 v0.1 = 핵심 3 화면 + index

도메인 분리 — 단건 vs 구독

구독 결제(04 결제/구독/v0.2/) = Pro 구독, 자동결제, plan picker, paywall, Trial.
단건 결제(04 결제/단건/v0.1/) = 식당 메뉴 1회성 결제, 라이언 추천 컨텍스트, 시간 슬롯, 시간 기반 환불.
공유: 결제수단 4종(토스·카카오·네이버·삼성) + 카드 fallback, PG 핸드오프 오버레이 패턴, 약관 동의 UI 토큰.
비공유: plan / trial / 다운그레이드 / 환불 정책 / 영수증 구조 / 결제 후 흐름(예약 확정).

v0.1 핵심 결정

라이언 추천 컨텍스트 보존이 정체성 — 진입 화면(01) 최상단에 노란 라이언 박스로 "왜 이 메뉴인가" 한 문단. 추상적 추천이 아니라 사용자 식습관·식당 컨텍스트 결합. 03 완료 화면에서도 같은 노란 박스로 닫음. "라이언 도메인의 따뜻함"이 결제 양 끝에 박힘.

결제는 "예약 확정"으로 잡음 — 사용자 관심은 결제 자체가 아니라 점심. 03 헤드라인이 "결제 완료"가 아닌 "예약이 확정됐어요" + "B카페에서 12:30에 만나요". 의인화 표현으로 트랜잭션 인상 줄임.

환불 정책 = 시간 기반 3단계 — 구독의 "기간 사용 후 종료, 환불 없음" 단일 정책과 다름. 단건은 예약 시간 기준 30분 전 / 5분 전 / 노쇼 3단. 02 결제 확인 단계에서 박스로 명시, 03 완료 단계에서 cutoff 시각(12:00)을 구체 시각으로 환산해 안내.

구독과 공유 — UI 토큰·PG·결제수단 — 사용자가 두 결제 도메인을 같은 결제 표면으로 인지하도록. 결제수단 row·약관 UI·CTA·PG 오버레이를 토큰 수준에서 일치. 학습 비용 ↓.

5분 전 알림은 도메인 약속 — 03에서 라이언이 "12:25에 알려드릴게요" 약속. 일정 알림(반복) 도메인이 아닌 단건 결제 자체에서 발화하는 일회성 이벤트 알림. 약속을 화면에 박는 이유 = 사용자가 결제 후 "이제 뭐 해?" 불안 해소.

미결 — v0.2 라운드 또는 후속

v0.1은 핵심 흐름 3 화면. 시니어 검토 라운드(구독 v0.1 → v0.2 패턴) 돌면 아래 항목들이 보강 대상.

  • 결제 실패 화면 (단건 변형) — 구독 v0.2 06과 같은 위상. 카드 잔액 부족·예약 슬롯 마감·식당 영업 종료 같은 단건 고유 사유 분기. 슬롯 임시 홀드 정책.
  • 식당 측 비동기 수락 모델 — 결제 즉시 자동 수락 vs 요청 → 식당 5분 내 수락/거절. 거절 시 자동 전액 환불 흐름. 헤드라인 분기.
  • 예약 상세 화면 (사용자 관리 진입점) — 구독의 04 hub와 같은 위상. 예약 후 사용자가 취소·변경·식당 연락하는 경로. 03 "예약 상세에서 취소" 링크의 도착지.
  • 환불 정책 cutoff 식당 협의 확정 — 30분/5분 시점은 v0.1 잠정값. 조리 시작 후 환불 불가 메뉴(찜·전골 등)는 별 정책 필요.
  • 다음 슬롯 노출 — 오늘 4 슬롯 외 내일·모레. 탭 / 캘린더 UX 결정. 슬롯별 잔여 자리 수 노출 여부.
  • 인원·수량 변형 — 2명 이상, 메뉴 2개 이상. 합계·약관(예약 정보 제공) 영향.
  • 메뉴 옵션 — 토핑·매운맛·드레싱 등 식당별 옵션. 01·02 합계 변화.
  • 영수증 PDF — 03에서 다운로드/공유. 경리·정산 케이스.
  • 길찾기 외부 지도 앱 선택 — 카카오맵·네이버지도·시스템 기본. 사용자 설정.
  • 보증금/예약금 분기 모델 — 일부 식당이 예약금만 받고 매장에서 잔액 받는 모델 채택 시. v0.1 가정과 별 흐름.
  • 시니어 SaaS 기획자 검토 라운드 — 구독 v0.1 → v0.2처럼 약점 5~7개 도출 후 v0.2 보강 계획.
